1. Verdict: what 180 hours buy
In 60 days at 3 hours a day you can build a single-PC pharmacy counter that is correct, not
a finished product: it works with the network unplugged, it cannot sell expired or over-
MRP stock, and every taka and tablet can be traced. It is ready for a parallel run on
throwaway data in a friendly shop. It is not ready for a paying shop.
Yes, the product is a SaaS and cloud platform; this sprint builds only its first layer, the
shop edge. The shop must trade offline indefinitely, so the counter, ledger and guards
come first and the cloud only follows what the shop sends. Sync, tenants, the Owner app
and the Super Admin console are phases P9 to P11 of the 15-phase plan. To avoid a rewrite
then, this sprint makes three cloud-ready choices from day 13: a tenant and branch id on
every business table, primary keys generated as time-ordered UUIDs in the app, and an
event row for every command carrying its tenant, branch and device.
On day 60 you will have
Screens for both counters: Counter 1 dispenses with first-expiry-first-out (FEFO) pick
suggestions, Counter 2 bills with split payments and a printed receipt.
A stock ledger by medicine, batch and location (Zone, Rack, Shelf, Bin) that is never
edited, only appended to, with balances derived from it.
Database triggers that refuse expired, over-MRP and non-sellable-rack sales, negative
stock and edits to history.
Receiving with quarantine and put-away, counts that become adjustments, loose-strip
and tablet sales.
Shifts, blind cash close and a Z-report.
A hash-chained audit log with a verify command, nightly backups and a tested restore.
On day 60 you will not have
Cloud sync, an Owner app or a Super Admin console. The shop works alone; the event
table is written from the start so sync can be added later.

2. Stack decision and architecture blueprint
Use Node.js with JavaScript, one Express process, one SQLite file and a React screen set
built against mocks first. It is the smallest stack where the database itself can refuse a
bad sale, nothing needs installing beyond Node, and almost every piece is something you
already use.

Two rules sit under all of it: money is an integer in poisha ( _minor ), and quantity is an
integer in base units, the smallest thing you sell, usually a tablet ( _base ). No floats
anywhere.
2.2 Why this gives speed and offline safety
One language, one repo, one process, one file. There is nothing to deploy and nothing
to call out to, so offline is the default and not a mode.
The zod schemas in packages/contracts are used three times: by the mocks, by the
API and by the tests. Screens and backend cannot drift.
The database is the last guard. A UI or API bug cannot corrupt stock because the
engine refuses the write.
Each phase adds roughly one new tool, so your learning curve stays flat until the last
phase.

2.4 The guards the database enforces
2.5 The path of one sale
1. Counter 1 searches or scans, the server returns the earliest-expiry valid batch with its
shelf code, and the dispenser sends a ticket.
2. The ticket appears at Counter 2 over SSE. The cashier claims it.
3. Pay sends one finalise-sale command with a client-generated idempotency key.
4. In one transaction the server re-picks the batch, writes the invoice, lines, payments,
ledger movements, audit row and event row. Any guard failure rolls everything back
and returns a stable error code.
5. The receipt prints from the browser.
Decision made for you: Counter 1's pick is advice, not a reservation. Stock is deducted only
at step 4, so if another sale took the batch first, Counter 2 gets a clear conflict and
Counter 1 re-picks. Reservations are a later feature.

3.3 The UI-first loop for one feature
1. Sketch the flow in Stitch or Figma: who, what they see, what they press.
2. Build the screen in React against an MSW mock whose shape is a zod schema in
packages/contracts .
3. Add the four edge states with the mock's switches: empty, loading, error with retry,
and refused by a guard with a plain sentence.
4. Write the failing test for the rule underneath.
5. Build the schema, trigger or route until the test passes.
6. Delete that mock handler. The screen must keep working unchanged; if it does not, the
contract was wrong, so fix the contract.
3.4 Edge states every screen must have
Empty (no tickets, no stock, no results) with the next action offered.
Loading that does not shift the layout.
Error with a retry button and a stable code in small text for support.
Refused by a guard: expired batch, over MRP, non-sellable rack, insufficient stock, each
with its own plain message in English and Bangla.
Offline banner for the browser-to-server link, which is local, so it only means the server
is down.
Usable with keyboard alone on both counters.
3.5 Definition of done for any day
3.6 When you fall behind
Stop at 3 hours. Write what is left as tomorrow's first item; do not stretch to 4 hours,
because tired code is where ledger bugs are born.
A gate day is your only buffer. If you are more than 2 days behind at a gate, use the cut
list in section 11 instead of compressing days.
The day's named test or checks pass, and npm test is green.
No console errors on the touched screens.
Every new screen has its four edge states.
A commit named Day N: <goal> is pushed and CI is green.
Three log lines are written. On gate days, also a 3-minute screen recording.

If better-sqlite3 fails to install, stop and fix it today: install your OS build tools or switch
to WSL2 on Windows. Every later day depends on it, and finding the problem now is the
most valuable thing Day 1 can do. A very new Node release can lack a prebuilt binary,
which makes npm compile from source and fail; if you see a long compiler error, switch to
the previous LTS. Pin the version in a .nvmrc file and let CI read it.
5.2 The smoke test: a trigger that refuses a write
Save as packages/db/smoke.test.js :
import Database from 'better-sqlite3';
import { test, expect } from 'vitest';
test('a trigger can refuse a write', () => {
const db = new Database(':memory:');
db.exec(`
CREATE TABLE t (qty INTEGER NOT NULL);
CREATE TRIGGER no_negative BEFORE INSERT ON t
WHEN NEW.qty < 0
BEGIN SELECT RAISE(ABORT, 'NEGATIVE_QTY'); END;`);
expect(() => db.prepare('INSERT INTO t VALUES
(-1)').run()).toThrow('NEGATIVE_QTY');
});
This is the whole idea of the project in ten lines: the database says no, whatever the
screen does.

5.5 Ten questions for a pharmacist
1. How does a sale move between the dispensing counter and the cashier today?
2. What do you do when the earliest-expiry strip is not on the front shelf?
3. Do you sell loose strips or tablets, and how do you price them?
4. Which fields on a batch label do you copy when goods arrive?
5. How do you handle near-expiry stock, and from how many months out?
6. What happens when MRP changes between two batches of the same medicine?
7. How is cash closed at night, and who counts?
8. What hardware is there: PC, scanner, receipt printer, drawer, and how often does the
internet fail?
9. How are returns and damaged stock handled?
10. Which records does the drug inspector ask to see, and who must be present when you

10. Phase E, days 53 to 60: audit integrity and edge hardening

Day 53. The audit chain
UI first: the audit log viewer on real data: who, what, when, which record, and a short
summary.
Hookup: audit_log (sequence, time, user, action, entity, canonical payload,
prev_hash , hash ), a canonicalJson function (sorted keys, fixed number format) and
SHA-256 from node:crypto , written inside every command's transaction by extending
runCommand . Triggers make the table append-only and require prev_hash to equal the
hash of the previous row; the first row uses 64 zeros.
Watch out: SQLite cannot compute the hash, so the app does and the trigger only
enforces the link. Never put a PIN or secret in a payload. If the audit write fails, the
business write must roll back with it.
Done when: a test over the list of commands shows each writes exactly one audit row,
update and delete are refused, and a forged prev_hash is refused.

Day 54. Verify and tamper tests
UI first: the Verify page: a green "chain intact through row N" or a red "broken at row K,
and why".
Hookup: verifyAudit(db) recomputes every hash and link and reports the first
break, exposed as npm run audit:verify . Tests on a copy with the triggers dropped:
flip one byte, delete a middle row, reorder two rows, truncate the tail. Print the latest
hash (the audit head) on every Z-report and store it in each backup manifest.
Watch out: a chain alone cannot see rows cut off the end, which is why the head hash
is anchored on paper and in backups. Make verification incremental from a saved
checkpoint once it takes long.
Done when: all four tampering cases are detected, truncation is caught against the
anchored head, and the time to verify 100,000 rows is recorded.
